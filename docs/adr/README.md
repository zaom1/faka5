# 架构决策记录 (ADR)

## ADR-001: 选择 Supabase 作为后端基础设施

**日期**: 2024-01-15  
**状态**: 已采纳  
**决策者**: 项目核心开发团队

### 背景

项目需要一个快速上线、低成本维护的后端方案，支持虚拟商品销售、订单管理和卡密自动发货。团队规模小（1-2人），需要尽量减少运维负担。

### 决策

选择 Supabase 作为核心后端基础设施，配合 Netlify 部署前端。

### 理由

1. **零运维成本**：Supabase 提供托管 PostgreSQL 数据库和 Edge Functions，无需自行维护服务器
2. **Serverless 架构**：按量计费，初期成本趋近于零，适合创业项目验证市场
3. **内置 RLS**：行级安全策略直接数据库层面控制权限，减少应用层安全漏洞风险
4. **TypeScript 原生支持**：Edge Functions 使用 Deno 运行时，与前端代码语言统一
5. **快速迭代**：数据库变更通过 SQL 脚本直接执行，无需复杂迁移工具

### 替代方案

- **传统方案**：Node.js + Express + 自建 PostgreSQL 服务器
  - 缺点：需要运维、服务器成本、SSL 配置、备份策略
- **Firebase**：Google 的 BaaS 方案
  - 缺点：NoSQL 数据库（Firestore）不适合复杂查询，RLS 不如 Supabase 灵活

### 注意事项

- Edge Functions 冷启动时间约 200-500ms，对支付回调场景可接受
- Supabase 免费层限制：50,000 行数据库、2GB 存储，后期需升级到付费层

## ADR-002: 前端采用原生 HTML/JS 而非框架

**日期**: 2024-01-15  
**状态**: 已采纳  
**决策者**: 项目核心开发团队

### 背景

前端需要实现商城页面和管理后台，团队希望快速交付且保持代码简洁。

### 决策

使用原生 HTML5 + Bootstrap 5 + Vanilla JavaScript，不引入 React/Vue 等框架。

### 理由

1. **项目复杂度低**：页面数量少（商城页 + 管理后台），无复杂状态管理需求
2. **加载性能**：无框架运行时开销，首屏加载快，适合 SEO
3. **开发效率**：无需配置构建工具（Webpack/Vite），直接编辑 HTML 即可
4. **维护成本**：原生 JS 代码直观易懂，后续接手者无需学习特定框架
5. **Bootstrap 5**：提供完善的组件和响应式布局，减少自定义 CSS

### 替代方案

- **React + Next.js**：适合大型项目，此处过度设计
- **Vue + Nuxt**：学习曲线低，但仍需构建工具和依赖管理

### 注意事项

- 页面逻辑超过 500 行时应考虑拆分到独立 JS 文件
- 避免内联事件处理（onclick 等），改用事件委托（当前为快速原型保留）

## ADR-003: 卡密支付后分配而非预扣

**日期**: 2024-02-10  
**状态**: 已采纳  
**决策者**: 项目核心开发团队

### 背景

初期实现中，创建订单时立即标记卡密为 used（预扣），但用户未完成支付时订单超时，卡密被无效占用，导致库存浪费。

### 决策

创建订单时只检查库存是否足够，不标记卡密。支付成功后的 webhook 回调中才分配卡密。

### 理由

1. **避免库存浪费**：未支付订单不占用卡密，提高库存周转率
2. **简化逻辑**：无需处理订单超时后的卡密释放逻辑
3. **幂等性保证**：webhook 可能多次回调，已支付订单直接返回成功，不重复分配

### 影响

- 创建订单时不返回卡密内容，支付成功后由 webhook 更新订单的 card_content 字段
- 用户需等待支付回调完成才能看到卡密（通常 1-3 分钟）

### 注意事项

- 高并发场景下可能出现竞态条件（同一批卡密被多个订单分配）
- 当前由数据库事务隔离级别保证，后续如订单量增加可引入 `SELECT ... FOR UPDATE SKIP LOCKED`

## ADR-004: 双模式演示架构

**日期**: 2024-03-05  
**状态**: 已采纳  
**决策者**: 项目核心开发团队

### 背景

项目需要展示给 HR/面试官体验，但部署环境可能未配置数据库或配置复杂。

### 决策

实现双模式：前端 Mock 模式（`?demo=true`）和真实数据库模式。

### 理由

1. **零配置体验**：Mock 模式内置示例数据，无需数据库即可体验完整流程
2. **真实功能展示**：数据库模式展示真实业务能力，包括持久化、权限控制
3. **隔离设计**：演示数据不影响真实数据库，demo 账号权限受限

### 实现方式

- Mock 模式：数据存储在 localStorage，刷新后重置
- 数据库模式：demo 账号标记为 `demo_admin` 角色，RLS 策略限制操作范围

## ADR-005: 密码存储采用 SHA-256 而非 bcrypt

**日期**: 2024-01-20  
**状态**: 已采纳（临时方案）  
**决策者**: 项目核心开发团队

### 背景

Deno Edge Functions 环境不原生支持 bcrypt，需要引入第三方依赖。

### 决策

暂时使用 SHA-256 + 盐值存储密码，计划后续引入 bcrypt。

### 理由

1. **环境限制**：Deno 标准库无 bcrypt，引入第三方库增加依赖风险
2. **快速交付**：SHA-256 实现简单，使用 `crypto.subtle.digest` 原生 API
3. **风险可控**：管理员数量少（通常 <10），被暴力破解的概率低（已有登录锁定防护）

### TODO

- 生产环境应升级为 bcrypt 或 Argon2
- 可在 Netlify 部署 Node.js 函数专门处理密码哈希

## ADR-006: 使用 Deno 而非 Node.js 作为 Edge Functions 运行时

**日期**: 2024-01-15  
**状态**: 已采纳  
**决策者**: 项目核心开发团队

### 背景

Supabase Edge Functions 支持 Deno 运行时，需要评估是否适合项目。

### 决策

使用 Deno 作为 Edge Functions 运行时。

### 理由

1. **Supabase 原生支持**：Edge Functions 默认使用 Deno，配置简单
2. **TypeScript 原生支持**：无需额外配置 tsconfig.json 或转译工具
3. **安全沙箱**：Deno 默认无文件系统/网络权限，需在 import map 中声明
4. **模块化导入**：通过 URL 直接导入依赖（如 `https://esm.sh/@supabase/supabase-js`），无需 npm

### 注意事项

- Deno 与 Node.js API 不兼容，不能直接使用 `require()` 或 `fs` 模块
- 第三方库需使用 ESM 格式或通过 esm.sh 转换
